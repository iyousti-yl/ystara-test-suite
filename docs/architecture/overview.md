# Ystara Test Suite: architecture overview

_Phase 1 version. Written so one person can maintain the whole system. Update it whenever a decision changes; the "Decisions" table is the log._

## What the system does

1. **Connect** to a customer's SAP Datasphere tenant, **read-only**: the Datasphere CLI for object definitions (`list` and `read` only) and a database user with read access for `SELECT` queries. Ystara never creates, changes, deletes or runs anything in a tenant.
2. **Discover** every object in the selected spaces and build a lineage graph (what reads from what, what writes to what, what triggers what).
3. Let users define **pipelines** (an output object and its upstream chain) and attach tests:
   - **Snapshots:** capture metrics of each object, compare across time or before/after a change.
   - **Scenarios:** simulate the pipeline's logic on fixture data, entirely inside one read-only `SELECT`, and evaluate assertions at checkpoints (see "How a scenario run works").
4. **Run** tests manually or on a schedule, **report** results, **alert** on failures.

## Key design decisions

| # | Decision | Why | Revisit when |
|---|---|---|---|
| 1 | TypeScript end to end | Datasphere CLI is a Node package; one language to maintain; UI5 Web Components are TS-first | Never, unless the CLI moves |
| 2 | Fastify API + Postgres + pg-boss | Small, well documented, no Redis to operate | Job volume exceeds what Postgres handles comfortably (very unlikely in year 1) |
| 3 | Connector behind an interface | Lets us ship a self-hosted runner later without touching api/worker | A security team asks for the runner |
| 4 | Metadata, hashes and aggregates only; no raw rows by default | Security reviews and GDPR (HR data at the first client) | A customer opts in to store N differing rows |
| 5 | Scenario spec is YAML validated by Zod; visual builder emits the same YAML | One artefact for devs and non-devs; Git-friendly | Never |
| 6 | **Strictly read-only.** The connector allows only CLI `list`/`read`, plus `config cache init` which only downloads the CLI's command list (enforced in `packages/connector/src/readonly.ts`), and SQL `SELECT` | Product promise to customers and Issam's requirement (2026-10-15); easiest possible security review | Never without an explicit product decision |
| 7 | Hosted in the EU (Hetzner or Scaleway), Docker Compose, Caddy (`deploy/`: Caddy is the only published port, secrets are files under `/etc/ystara/secrets`, nightly `pg_dump` encrypted with restic to object storage at another provider, a weekly restore test; runbook in `deploy/README.md`) | Budget under €200/month, GDPR | Beyond ~30 tenants, move to managed Postgres and two VMs |
| 8 | Email + TOTP auth in v1, SSO in v2 | Keep v1 small; SSO is a known enterprise ask | First enterprise procurement |
| 9 | Scenario tests are **read-only simulations**: fixture rows are inlined into a single `SELECT` that reproduces the pipeline's SQL logic | Keeps decision 6 for scenarios too (chosen by Issam, 2026-10-15) | Customers ask for coverage of flow types that can't be expressed as SQL |
| 10 | Lineage is found by scanning definitions for names of known objects, with role rules per type, not by a parser per object format | Flow and task chain JSON differs between CLI releases; this survives format changes | Real samples show false or missing edges |
| 11 | Plain SQL (node-postgres) with numbered SQL migrations, no ORM; tests run on PGlite (Postgres in WebAssembly) | Every query readable as written; tests need no database server, on Windows too | Queries get repetitive enough that a query builder pays off |
| 12 | Pipelines are stored as an output plus writer exclusions; their steps are computed from the latest successful scan | Steps follow the tenant as it changes, and nothing goes stale | Tests attach to steps (phase 2), which may need stored step lists per scan |
| 13 | Local settings: app settings and secrets in `.env.local`; `.env` holds only the `YSTARA_*` host ports (Postgres 55432, API 4000) that Compose substitutes. Programs refuse a database without Ystara's migrations | Compose never sees a secret, and no tool silently uses another Postgres on the machine | Hosting (decision 7) brings a secrets store |
| 14 | One origin: the API serves the web app at `/` and itself under `/api` (Vite forwards `/api` in development). No CORS | No cross-origin calls to secure; one port to publish and, later, to put behind sign-in | The web app needs a CDN or its own host |
| 16 | Sign-in is email + password (scrypt) + a mandatory authenticator code (TOTP, RFC 6238); server-side sessions in an HttpOnly, SameSite=Strict cookie; no public sign-up, accounts are created by the operator (`npm run account:create`) and people join by one-time invitation links. Ystara's operator (a flag on the user, set only by `npm run operator:grant`) has a panel across all accounts that shows counts, never tenant data, and makes one-time reset links for a lost password or phone. Every API route checks a permission from `packages/shared/src/roles.ts` and only sees its own account (another account's ids answer 404) | Small, no identity provider to run or pay for, and strong enough for the first customers' security reviews (Issam chose "You create them" and an operator panel besides each account's admin page, "Both", 2026-10-16) | First enterprise customer that needs SSO (decision 8) |
| 15 | The web app loads nothing from third parties: its fonts (IBM Plex Sans and Mono, the youlytics typefaces) are bundled from Fontsource and UI5's own font download from its CDN is off, and the API's Content-Security-Policy only allows fonts and styles from Ystara itself | GDPR (no visitor IPs to a CDN) and works offline; the policy blocks a regression instead of letting it leak | Never |
| 17 | The worker logs in to each tenant with a **technical OAuth client** (purpose Technical User) that the customer's admin creates and enters in the Connect wizard. Its secret is sealed with `MASTER_KEY`, never sent back, and opened by the worker for one job at a time in a temporary CLI folder; the token URL must be on SAP's sign-in service | Scans (and later scheduled runs) need nobody present, a person's login expires, and tenants never share a login (Issam chose "Technical client", 2026-10-16) | A customer wants the self-hosted runner (decision 3), or SAP changes how the CLI logs in |

## Data model

In place (`packages/db/migrations/`):

- `accounts` (customer organisations) → `memberships` (user, role) → `users` (email, scrypt password hash, encrypted authenticator secret, last code used, operator flag)
- `invitations` (account, email, role, token hash, expiry, accepted at) and `sessions` (token hash, user, account, verified by code or not, expiry). Only hashes of links and cookies are stored
- `sign_in_resets` (user, operator who made it, token hash, sealed authenticator secret, expiry, used at): one-time links from the operator panel to choose a new password and authenticator, kept on record
- `tenants` (account, name unique per account, host) → `tenant_connections` (the technical OAuth client: client ID, secret encrypted with `MASTER_KEY`, token URL, status checking/connected/failed, the spaces to scan as the admin named them, each with its last check: readable, not readable with the CLI's error, or not checked yet, who changed it)
- `scans` (tenant, spaces, source tenant/import, status queued/running/succeeded/failed, counts, warnings, error) → `scan_objects` (space, name, type, CLI kind, definition hash) and `scan_edges` (from, to, kind)
- `object_definitions` (tenant, hash, definition JSON): each distinct definition once per tenant, as it was read (`json`, not `jsonb`, keeps the order of a table's columns)
- `pipelines` (tenant, name, output, writer exclusions)
- `space_database_users` (tenant, space, host, user name, password encrypted with `MASTER_KEY`, status checking/connected/failed, the views and tables it saw at its last check, who changed it): one per space, for snapshots
- `tenant_snapshot_salts` (tenant, salt encrypted with `MASTER_KEY`): the salt of every snapshot hash of a tenant, made once
- `snapshots` (tenant, pipeline, the scan whose steps were measured, status queued/running/succeeded/failed, who asked, when, error) → `snapshot_objects` (each step in order: definition hash, measured/not measurable/failed with the reason, row count, per-column measures JSONB, time taken)
- `scenarios` (tenant, pipeline, name unique per pipeline, the ScenarioSpec as JSONB, who saved it and when) → `scenario_runs` (the spec as it was asked for, the scan compiled, status queued/running/passed/failed/error, what stood in for each step, each check's result, passed and total, error, the suite it ran in)
- `scenario_suites` (tenant, pipeline, cause manual/scan, the scan that queued it and the steps it changed, status, how many runs passed of how many) → `scenario_alerts` (the scenarios that broke, email status and recipients, Teams status)
- `tenant_scan_schedules` (tenant, cron line, time zone, next run); `scans.scheduled` marks the scans it made
- `teams_channels` (account, the webhook address encrypted with `MASTER_KEY`, its host, who set it); `snapshot_alerts` also has a Teams status
- `audit_events` (account, or none for the operator panel; user and their email as it was; when; the action; what it acted on with its name read before the request ran; the request fields the action lists; the IP address). Written only, never changed or deleted by the app
- `memberships.spaces` and `invitations.spaces`: null for every space, or the space IDs a member sees
- `pipeline_signoffs` (tenant, pipeline, approved or rejected, comment, the scan, latest suite and latest successful snapshot it covered, who signed and their email, when)
- `sessions.last_seen_at`: when the session was last used (moved at most once a minute); a session ends after 60 minutes without use, and after 12 hours at most
- `accounts.drafting_with_claude`: whether the account's admin agreed to send pipeline definitions to Anthropic for drafting; off until they do
- `worker_heartbeats` (worker, version, started, last seen): each worker's sign of life at every schedule tick, read by `/api/health/worker`
- `server_secrets` row `master_key_check`: a known value sealed with `MASTER_KEY` at the first start, so a program started with another key stops at once
- Migration 015 also indexes every foreign key that a delete cascades through or a page reads by (scenario runs by pipeline, snapshots and suites by scan, and so on)

Planned:

- `pipeline_steps` if tests need stored step lists
- scenario fixtures from an uploaded CSV

Secrets are encrypted with `MASTER_KEY` (AES-256-GCM, `packages/shared/src/secrets.ts`: authenticator secrets, tenant client secrets, database user passwords, snapshot salts and Teams webhook addresses). The key lives alone in the git-ignored file `.master-key`, which Docker Compose passes as a secret to the API and the worker; a hosting platform can set `MASTER_KEY` instead. The API seals a client secret for its tenant (the tenant ID is the additional authenticated data), a database password for its tenant and space, and a Teams webhook address for its account, and the worker seals a tenant's snapshot salt for that tenant; only the worker opens them, for one job at a time (the API opens the webhook address too, to post a test card). Rotating the master key re-encrypts rows in a migration.

## Sign-in and accounts (phase 1d)

1. The operator runs `npm run account:create -- --name <Account> --admin <email>`, which prints a one-time link for the account's first admin.
2. Opening the link, a new user chooses a password and scans a QR code with an authenticator app. The server makes that secret and keeps it (sealed) on the invitation; the first code from the app proves it works and creates the user. Someone who already uses Ystara in another account signs in as that email and joins; their role elsewhere, or in this account if they already belong to it, never changes.
3. Signing in takes the password (a 10-minute "pending" session), then a code (a new 12-hour session: the cookie changes). Each code works once. Wrong codes count per user across sign-ins: five in a row lock codes for a minute, then 2, 4, ... up to an hour, and end the sign-in. Each attempt is counted before its code is checked, in the same statement as the lock check, so requests sent at the same moment can't try more codes. Login, code and invitation routes allow ten tries a minute per address and per email, user or link, so one client can't lock out a whole office. Behind a proxy, `YSTARA_TRUST_PROXY` says which proxy may report the client's address. Invitation tokens never reach the log. Changes from another site's pages are refused (Origin check, on top of the SameSite cookie).
4. Admins manage their account on the Users and roles page: invite by email and role, change roles, remove people, rename the account (names are unique across Ystara). An account always keeps one admin. Removing someone ends their sign-in to that account at once.
5. The web app hides what a role can't do, but only the API enforces it (`config.access` on every route, `apps/api/src/auth/access.ts`).
6. The operator (`npm run operator:grant`) runs the Operator page: every account and user with counts, creating and renaming accounts, inviting an admin to an account that has none left (never to one that still has an admin, so the operator can't make themselves admin of a customer, and never someone already in the account, whose role an invitation can't change), and reset links. A reset link (valid 3 days, one at a time per user, never for an operator) lets someone choose a new password and set up their authenticator again; using it signs out every browser signed in as them. Each link records the operator who made it and when it was used, goes into the log, and shows on the Users and roles page of the person's accounts ("Sign-in reset by Ystara on ..."): every link of the last 30 days, used, open or never used, so a newer link never hides an earlier one. Ystara still sends no email: the operator passes the link on after checking who asks.

## Connecting a tenant (phase 1e)

1. An admin adds a tenant by its Datasphere URL, and the app opens **Connect**. The URL must be `https://<tenant>.<region>.hcs.cloud.sap` (no IP address, other host, port, path or query), because the worker sends that host a bearer token and the Technical client page shows what it answers. Connect says what a Datasphere admin does once: create an OAuth client with the purpose Technical User (System › Administration › App Integration), copy its client ID, secret and the token URL, and add its technical user to each space to scan with a scoped role that can read the space's objects (e.g. Viewer). The admin then enters the client and the IDs of the spaces to scan (up to 20).
2. The API stores the client with the secret sealed and the spaces unchecked (`PUT /api/tenants/:id/connection`, admins only), sets it to "checking" and queues a `connection-check` job. `PUT /api/tenants/:id/connection/spaces` changes only the spaces, without the secret, and checks again. It accepts only a token URL on SAP's sign-in service (`https://<subdomain>.authentication.<region>.hana.ondemand.com/oauth/token`; not an app on SAP's cloud platform such as `*.cfapps.….hana.ondemand.com`), so no secret can be sent elsewhere. The secret is sealed for that tenant (its ID is the AES-GCM additional data), so a sealed secret copied into another tenant's row doesn't open. It is never sent back, not even to admins. Both URL rules are in `packages/shared/src/urls.ts`.
3. The worker checks both URLs again (rows saved before the rules), opens the secret, writes it to a secrets file in a new temporary CLI folder (readable by its own user only), downloads the CLI's command list, then lists one view and one local table of each space (`objects views list --space <S> --top 1`, the same for `local-tables`), and deletes the folder. It records a space as readable only when both calls print a list (an error object or a question, even with exit code 0, is a failure), otherwise as not readable with the CLI's last lines; the connection is "connected" when at least one space is readable, and "failed" when none is or the login itself failed (then with the login's error). A verdict for a client or space list that was changed meanwhile is dropped. It doesn't use `spaces list` or `spaces read`: on CLI 2026.21 both need a tenant-wide privilege that a technical client limited to its spaces doesn't have, while the object commands work in the spaces it is a member of.
6. An admin can delete a tenant (`DELETE /api/tenants/:id`, `deleteTenant` in `@ystara/db`). Its row goes, and with it, through foreign keys that cascade, everything Ystara stored for it: scans with their objects and edges, object definitions, saved pipelines, snapshots with their steps, the technical client with its sealed secret, the database users with their sealed passwords, and the snapshot salt. Nothing in the Datasphere tenant is touched. A job still queued for it finds nothing when it starts and stops. The dialog lists what goes before anything is deleted.
4. Scans of a tenant with a client log in the same way, one temporary folder per job, and may read only the spaces its last check found readable: the scan dialog offers only those, and `POST /api/tenants/:id/scans` refuses any other (409). A worker that starts deletes such folders older than 6 hours (longer than any job runs), which a killed worker left behind with the secret in them. A tenant without a client is not scanned: the scan fails with "This tenant is not connected". Only a worker started with `YSTARA_WORKER_MACHINE_LOGIN=1`, on a developer's own computer, uses that computer's CLI login instead; a shared worker never does, or every account's tenants would be read with one person's rights.
5. The CLI starts with an environment of its own: `PATH` and the other variables a process needs on Windows and Linux, proxy and CA settings, and its home folders pointed at the temporary folder. Nothing else of the worker's environment (`MASTER_KEY`, `DATABASE_URL`) reaches it. Everything it prints that is stored or shown (connection errors, scan errors and warnings) goes through `maskSecrets` in the connector: the client's secret as it is, URL-encoded and in base64 (also as `clientId:secret`), and anything shaped like a credential (Bearer and Basic headers, JWTs, `access_token`/`refresh_token`/`client_secret` values).

## Reading a space with SQL (phase 2, in progress)

Snapshot tests measure views with SQL, through a database user of the space (Space Management > Database Access, with read access only). `packages/connector/src/sql.ts` connects with hdb, SAP's open-source JavaScript client (TLS on port 443), and sends only statements that pass `assertSelectOnly` (one SELECT: no semicolon, comment, INTO or row lock; values as `?` parameters). `metricsQuery` measures an object in one pass: the row count and, per column, non-null and distinct counts, min and max for ordered types and a sum for numbers. Integer and `DECIMAL(p,s)` columns are summed exactly at their own scale; floating types (DOUBLE, REAL, DECIMAL without a scale) as `SUM(CAST(c AS DECIMAL(38, 6)))`, because a floating sum's last digits depend on the order HANA adds the rows in. Each value is rounded to 6 decimals once and then added exactly, so the same data always gives the same sum, and the scale is stored with it (`sumScale`). Min and max leave the tenant's database only as a salted SHA-256 made there (`HASH_SHA256`), and so does the sum of an object with fewer than 10 rows (Issam's GDPR choice, see the decisions log). Only these results are stored, never rows. `npm run spike:sql` checks a database user on a real tenant.

**Database users (phase 2b), under Connection in the app.** An admin adds one database user per space (Datasphere names them SPACE#SUFFIX and each reads only its own space, so the space comes from the name): host, user name and password. The host must be `<id>.hana.<region>.hanacloud.ondemand.com` (`hna1`, `hna2`… in place of `hana` on newer tenants), because the worker sends it the password; the API, the worker and `SqlReader.connect` all check it. The password is sealed for that tenant and space and never sent back. The worker's `database-check` job (`checkDatabaseUser` in the connector) signs in once, fails a user with any privilege on the space's schema beyond SELECT, SELECT METADATA and SELECT CDS METADATA, and stores the views and tables it sees there. The Database users page lists each user with its status, what it sees, and why a check failed. Anyone who can scan may check one again. Each pipeline page marks the steps a snapshot can measure, from that list only (`measurability` in `@ystara/shared`), and says for each other step why not: a flow or task chain, no database user for its space yet, not checked, a failed check, or not exposed for consumption (with the hint that a modeler can expose a view).

**Snapshots (phase 2c).** On a saved pipeline, anyone who can run tests clicks **Take snapshot**. When no step is measurable, the API refuses and the pipeline page says why in one sentence (`whyNothingMeasurable` in `@ystara/shared`): a tenant with only imported scans has no database user at all, otherwise the first that applies of no database user for a space, a failed check, a check still to come, or nothing exposed for consumption. The worker's `snapshot-capture` job (`runSnapshot`) takes the steps from the tenant's latest successful scan, as the pipeline page does, and stores every step in order: its definition hash in that scan, and either its measures, the reason it can't be measured, or the error that stopped it. Each space's user signs in once per snapshot, only for a space with something to measure; `measureObject` reads the object's columns from `sys.view_columns` or `sys.table_columns` and runs `metricsQuery` with the tenant's salt. A failed sign-in fails that space's steps without a second try. The snapshot fails when a measurable step couldn't be measured, or when none could be, and keeps what was measured. The pipeline page lists its snapshots; a snapshot's page shows each measured object's columns (min, max and small sums as the first characters of their hash) and what happened to every step.

**Comparing snapshots (phase 2d).** `compareSnapshots(before, after)` in `@ystara/shared` compares two stored snapshots of one pipeline, step by step, from what they stored and nothing else; `GET /api/pipelines/:id/compare?from=&to=` returns it (the latest two successful snapshots without a pair; no tenant call, nothing stored). A step measured in both gets its rows, and per column its non-null, distinct and sum before and after with the difference and percentage, min and max (and a small object's sum) as changed or unchanged since only their hashes exist, and the columns added, removed or of another type. Counts and hashes compare exactly. Sums compare exactly as numbers at the larger of the two scales they were taken at, so "12.50" equals "12.5" and a one-cent change shows; a snapshot from before `sumScale` existed counts 0 decimals for integers and 6 for the rest. A step's definition changed when its definition hash differs (between the two scans the snapshots used); its data changed when its rows, a column measure or its set of columns differ. Steps measured in only one snapshot are listed apart with the other's reason; steps measured in neither still have their definitions compared; a step in only one snapshot means the pipeline changed and counts as a changed definition. The pipeline's verdict is unchanged, data changed, definition changed or both. The **Compare** button in a pipeline's Snapshots section opens `/pipelines/:id/compare`: two snapshot pickers, the verdict, the lineage picture with each step's result on its node, the changed steps with their changed columns, the unchanged ones folded away, then the steps that couldn't be compared.

**Scheduled snapshots (phase 2e).** A saved pipeline can have a schedule: a cron line of five fields (minute, hour, day of the month, month, weekday) read in an IANA time zone such as Europe/Brussels, set on its Snapshots tab by anyone who can run tests (`PUT /api/pipelines/:id/schedule`). `checkSchedule` in `@ystara/shared` checks it the same way in the API and in the dialog, which shows the next five runs while the line is typed: five fields, a real time zone, at least one run, and runs at least 15 minutes apart, because each run reads every measurable step. A pipeline nothing can be measured in can't get a schedule, for the reason Take snapshot gives. The schedule is a row of `pipeline_schedules` with its next run. Once a minute, pg-boss's own cron sends the job `snapshot-schedule-tick` (one per minute, whichever worker sends it), and the worker that takes it locks the due schedules (`for update skip locked`), queues a snapshot marked `scheduled` for each, and moves each next run to the first one after now, all in one transaction with the snapshot jobs themselves (pg-boss sends them on that transaction), so a crash leaves neither a snapshot without its job nor a run taken twice. Runs missed while no worker ran are taken once, when one is back. A run is skipped while the pipeline's previous snapshot is still queued or running, unless that one is more than two hours old and taken as stuck, and on a tenant made from imported scans, which has no database. Daylight saving follows cron-parser: a run in the hour the clock skips runs an hour later, and one in the hour that repeats runs once. The Snapshots tab says when a run is more than five minutes late, which means no worker is taking the schedules.

**Alerts on scheduled snapshots (phase 2f).** When a scheduled snapshot finishes, the worker queues `snapshot-alert`. `alertReasons` in `@ystara/shared` compares the snapshot with the pipeline's previous successful one (`compareSnapshots`) and returns why it calls for an alert, most pressing first: it failed (with the failed steps' names, never the database's error, which can quote a value); the output went empty, or lost more than the schedule's `row_drop_percent` of its rows (20 by default); a step's definition changed; a measured step gained, lost or retyped columns; steps were added to or removed from the pipeline. Other data changes only show on the compare page. A definition changes between scans, and scans are not scheduled, so a changed definition is noticed by the first scheduled snapshot after someone scans. When there is a reason, the job stores it in `snapshot_alerts` and sends one plain-text email, all recipients in Bcc, to the pipeline's watchers (`pipeline_watchers`) who are still members of its account. Whoever saves a pipeline watches it; anyone in the account can Watch or Unwatch it. The mail server is `SMTP_URL` (nodemailer); without one, or without watchers, the alert is stored with that status and shown on the snapshot page. An alert that was sent, or had nobody to go to, is never sent again; a failed send is stored with the server's answer and tried again by pg-boss three times, a minute apart and then longer. Docker Compose runs Mailpit as a local inbox.

**What a database user can read** (Issam's run, 2026-10-17): SELECT on the space's schema, but only the **views exposed for consumption**. No other view and no local table is visible, so of a pipeline usually only its output can be measured. That shapes phases 2 and 3:

- **A snapshot measures what is exposed.** A pipeline snapshot measures its exposed outputs and any exposed intermediate view. The pipeline page shows for each step whether SQL can measure it, from what the database user actually sees (the connection check lists it), never from an assumption that tables are readable. A step that isn't measurable says so and why ("not exposed for consumption"). **Ystara never exposes anything itself**; at most it tells the admin which views they could expose.
- **Every step still gets checked, from its definition.** The CLI reads every object's definition, so a scan-to-scan comparison shows schema and logic changes for all steps, measurable or not. SQL adds the data side for the exposed ones.
- **Phase 3 can't read intermediate views either.** So a simulation must not read any tenant object at all; see "How a scenario run works" below.

## How discovery works (phase 1)

1. For each space and each object kind, `list` then `read` every object (CLI, read-only, a few in parallel). One unreadable object becomes a warning; the scan carries on. Spaces are given by their IDs: Ystara never lists the tenant's spaces, because `spaces list` and `spaces read` need a tenant-wide privilege that its technical client shouldn't have.
2. Classify each object (`views` is split back into SQL and graphical views) and hash its definition so re-scans show what changed.
3. Find references: walk each definition and match strings, and identifiers inside SQL text with comments removed, against the names of all scanned objects. Role rules: in flows, each step's `component` decides (`...producer`, `...target` write; `...consumer`, `...source` read), keys of a `targets` section are writes, and elsewhere a key path containing "target" means a write; in task chains, references are steps; in tables, views and analytic models, references are reads. A flow reading its own target (delta, lookup) is not a dependency. When a `read` bundles dependency definitions, only the object's own entry is scanned.
4. Build edges that point the way data moves (`reads_from`, `writes_to`) plus control edges from task chains: `triggers` for a step they run, `clears` for a table a step empties (DELETE_DATA).
5. A **pipeline** for an output object is traced backwards through data edges: what it reads (main chain and side inputs alike), the flow that writes each table, down to tables nothing upstream writes. Task chains are never followed. Writers excluded by configuration are listed, not followed; a table still left with several writers is reported as ambiguous. Steps are topologically sorted and loops are reported, not hidden. **Entry points** are tables with no other table upstream (where fixtures go).

Try it locally: `npm run scan -- --space <SPACE> --output <OBJECT>` writes a Mermaid lineage diagram to `tools/scan/output/`.

## How a scenario run works (phase 3, read-only simulation)

Nothing is written to the tenant and no flow or task chain is run. Instead the platform tests the **logic** of the pipeline. **The query it runs reads no tenant object**, only fixtures inlined into the statement (and `DUMMY`): a standard database user sees only exposed views (above), so a simulation that needed SELECT on the pipeline's own views and tables would fail on a real tenant. Each step's logic comes from its definition, read with the CLI by the scan, not from the database:

1. Load the scenario YAML and the pipeline.
2. Turn each table's fixture rows into an inline data set (`SELECT ... FROM DUMMY UNION ALL ...`). A table the scenario gives no rows for is empty, and rows given for a table that a transformation flow loads stand in for that flow, so a scenario can start in the middle of a pipeline.
3. Walk the pipeline from the entry points to each checkpoint and compose one query: every view and SQL-based transformation flow is compiled from its definition (the SQL of a SQL view; the CSN `query` of a graphical view) into a nested subquery, with its references to upstream objects rewritten to the parts that replace them. A table loaded by a transformation flow is represented by that flow's `SELECT` (full-load semantics). **Any reference that resolves to neither a fixture nor a compiled step stops the run** before anything is sent (a lookup or dimension outside the pipeline needs a fixture too), so the composed query can never fall back to reading a real object. Issam kept `assertSelectOnly` without `WITH` (2026-10-19), so each step's query is nested wherever it is read, and a step whose query would bind more than 32,767 values (SAP HANA's limit for one statement) stops before anything is sent.
4. Turn each assertion into one SELECT over its checkpoint's composed query (a count, the rows with an empty value, the duplicated keys, an aggregate, the rows themselves, or the scenario's own SELECT over `{{checkpoint}}`), run it through the read-only database user, and judge what comes back (`planScenario` and `runScenario` in `packages/connector/src/simulate/scenario.ts`). Phase 3a runs a scenario file from the command line (`npm run scenario:run`). Phase 3b stores scenarios in the app, where the builder makes them (below) and the worker runs them (`apps/worker/src/jobs/scenario-run.ts`) through any connected database user of the tenant, since the checks read nothing but `DUMMY`. They run again on their own after a scan that changes the pipeline (below).
5. Steps that cannot be expressed as SQL (data flows with script operators, replication flows, remote sources) stop the simulation at that point with a clear message; those parts of the chain are covered by snapshot tests instead.

### The scenario builder (phase 3b)

A saved pipeline's Scenarios tab lists its scenarios with their latest run. The builder (`apps/web/src/pages/Scenarios.tsx`, `apps/web/src/scenario/`) edits one ScenarioSpec, the same shape as a file:

- **Test rows:** one grid per table that takes rows (`GET /api/pipelines/:id/scenario-inputs`, from the latest scan's definitions), with the table's columns and types. Each cell is typed text, turned into a value by its column's type (`cellFromText`); an empty cell is NULL. Rows pasted from a spreadsheet fill the grid from the cell, by column name when the first line is a header. A table given no rows gets no fixture and is empty.
- **Checks:** added per step in a dialog (row count, no empty values, unique, an aggregate, exact rows, SQL), with the step's columns to pick from.
- **Compile as you go:** the draft is sent, unsaved, to `POST /api/pipelines/:id/scenario-check`, which compiles it on the latest scan and says what stops it or a check. Nothing is sent to the tenant.
- **Run:** `POST /api/scenarios/:id/runs` refuses (409, with the reason) a scenario that can't run, and otherwise queues a `scenario-run` job. The run keeps the scenario as it was, and its page shows each check's result and what stood in for each step.
- **As a file:** the builder shows the scenario as YAML to copy into a `.local.yaml` file for the CLI or Git, and loads one back.
- **The columns that matter (phase 3c):** each table column comes with what the pipeline's logic does with it (`key`, `used`, `joined`, `keeps` a filter value, a validity `range`; `columnUsage` in `packages/connector/src/simulate/usage.ts`, reading each step's SQL or CSN by name). A grid shows the keys and the columns read, the rest on request; added rows start with values that get through (`prefillText` in `apps/web/src/scenario/model.ts`).
- **Excel (phase 3c):** the test rows as a workbook, one sheet per table, and the same file read back (`apps/web/src/scenario/excel.ts`), in the browser.
- **Drafting with Claude (phase 3c):** `POST /api/pipelines/:id/scenario-draft` sends the description and the pipeline's definitions to Claude and gets rows and checks back, compiled and corrected up to three times, never saved (`apps/api/src/drafting.ts`). Only when the operator has entered an Anthropic API key on the operator panel (`/api/operator/claude`, sealed in `server_secrets`) or the API has `ANTHROPIC_API_KEY`. No tenant data goes out: Ystara has none.

Who may do what: everyone in the account reads scenarios and runs (`scenarios.read`, `runs.read`); developers, test coordinators and admins save them (`scenarios.write_visual`) and run them (`runs.execute`).

### Regression runs: suites, nightly scans and their alerts

- **Run all** (`POST /api/pipelines/:id/scenario-suites`) queues a suite: a run of each scenario of the pipeline, made in one statement with the suite (`createScenarioSuite`). The `scenario-suite` job runs them one after the other by name (`apps/worker/src/jobs/scenario-suite.ts`), sharing one sign-in per database user, and finishes the suite from its runs: passed when all passed, failed otherwise, error when it couldn't run.
- **After a scan** that succeeded, of a tenant with a Datasphere URL, the scan job calls `queueSuitesAfterScan` (`after-scan.ts`). For each saved pipeline with scenarios, `changedSteps` (`packages/connector/src/discovery/changes.ts`) compares the steps' definition hashes in the scan its scenarios last ran on (or the tenant's scan before) with the new scan, and a suite with cause `scan` and the changed steps is queued on the same transaction as its job. Skipped: no change, no connected database user, a suite still queued or running (less than 3 hours old).
- **Scan schedules** (`/api/tenants/:id/scan-schedule`, Discovery) work as snapshot schedules do, at least 4 hours apart (`MIN_MINUTES_BETWEEN_SCANS`); the same minute tick (`runScanScheduleTick`) creates a scan marked `scheduled` of the spaces the technical client could read, unless the tenant's last scan is unfinished (and less than 5 hours old) or the client can read none.
- **Scenario alerts** (`scenario-alert` job): after a suite with cause `scan` that didn't pass, `brokenScenarios` in `@ystara/shared` lists the runs that failed or couldn't run where the scenario's run before passed, or there was none. The alert is stored, emailed to the watchers and posted in Teams, as snapshot alerts are; a suite started by hand never alerts.
- **Teams** (`/api/account/teams-channel`, the Alerts page, admins only): one channel per account. The address must be one of Microsoft's webhook hosts (`teamsWebhookHost`); a test card is posted before it is kept, sealed for the account. `deliverAlert` (`apps/worker/src/jobs/deliver.ts`) sends the email, then the Adaptive Card (`teamsPayload`), keeps the two statuses apart and lets pg-boss retry the one that failed.

### Audit log, sign-off and access per space (phase 4a)

What a design partner's auditors and admins ask for before a pilot.

- **Audit log** (`apps/api/src/audit.ts`, `AUDIT_ACTIONS` in `packages/shared/src/audit.ts`). After each request that changed something answers below 400, one `audit_events` row says who did what, to what, when and from which address; each sign-in (after the code) and each switch of account too. What a request acts on is read before it runs, so a deleted pipeline keeps its name in the log. Only the body fields the action lists are kept (a name, a role, spaces, a verdict and its comment), never a secret, a webhook address or test rows. Every route that isn't a GET must be in `AUDIT_ACTIONS` (or listed as null, for one that changes nothing, such as compiling a draft): the API refuses to start otherwise, so a new route can't go unlogged by mistake. Operator panel events belong to no account. Admins read it on the Audit log page (`GET /api/audit`, newest first, 100 a page, filters by person, group and days; `GET /api/audit.csv`, up to 50,000 events); nothing in the app changes or deletes an entry.
- **Access per space.** A member other than an admin can be limited to some space IDs (`memberships.spaces`), in every tenant of the account, since a space ID such as HR usually names the same team's space in DEV and PROD. One place checks it for every route (`apps/api/src/scope.ts`): a pipeline belongs to its output's space, and a member who sees that space sees the whole pipeline, upstream steps in other spaces included, because a test needs all of them (`GET /scans/:id/objects/...?within=SPACE.OUTPUT` opens such a step). Anything else answers 404, as if it didn't exist. Scans and their graphs list only the member's spaces; scan schedules need every space, because a scheduled scan reads all of them; database users are listed and checked per space. Tenants themselves are not limited.
- **Sign-off** (`POST /api/pipelines/:id/signoffs`, `results.sign_off`: test coordinators and admins). Approve, or reject with a reason, a pipeline as it stands: the sign-off records the scan its steps came from, its latest finished suite and its latest successful snapshot. It is **outdated** once a later scan changes any of its steps (`changedSteps`, the same comparison that queues suites after a scan); the pipeline page then shows "Approval outdated" and which steps changed. A later sign-off replaces it; the earlier ones stay in the history.
- **The Pipelines board** (`GET /api/tenants/:id/pipeline-summaries`, `runs.read`). One query (`pipelineSummaries` in `packages/db/src/summaries.ts`) gives each pipeline its latest suite, latest snapshot with its output's rows and alert, schedule, latest sign-off and whether the user watches it; the route marks an approval outdated as the sign-off page does (`changedSteps` against the latest scan, each scan's graph loaded once). `pipelineHealth` in `@ystara/shared` turns a summary into one state (failing, changed, untested, running, ok, most pressing first), a sentence and the next step; the web app sorts the board by it and shows it on Home and above a pipeline's tabs. Nothing here calls the tenant.
- **History and report.** `GET /api/pipelines/:id/history` puts suites, scenario runs, snapshots and sign-offs on one timeline (the History tab, with two charts and a CSV of the whole timeline). `GET /api/pipelines/:id/report` gathers what an auditor reads: the sign-off and what it covered, the latest suite with every check, the latest two snapshots compared, the steps and the recent history. The web app shows it on a page without the menu, to print or save as PDF from the browser. Nothing here calls the tenant.

Open questions for phase 3: how delta loads and upserts in transformation flows should be simulated; how far a compiler from the CSN `query` of graphical views to HANA SQL can go (joins, unions, calculated columns, aggregation, parameters), which can't be tested against the deployed SQL of exposed views, because `SYS.VIEWS` gives the database user no definition (the spike's run, 2026-10-19), so only a view's columns are checked against `SYS.VIEW_COLUMNS`; which steps can't be inlined into one SELECT (SQLScript views and table functions, currency conversion that reads TCUR tables, `CURRENT_DATE` and session values, which need fixed fixture values). A phase-3 spike should compile one SQL view and one graphical view of a real pipeline into a fixture-only SELECT and run it through the database user before the engine is built. That compiler is in `packages/connector/src/simulate` (`simulatePipeline`), and `npm run spike:simulate` runs it on a saved scan, with `--run` through the database user and `--oracle` against the deployed SQL of exposed views (README, "Simulating a pipeline"). It uses nested subqueries, so `assertSelectOnly` is unchanged.

## Security posture (short form for the security pack)

- Read-only by design: CLI limited to `list`/`read` in code (plus `config cache init`, which only fills the CLI's local list of commands), database user with `SELECT` rights only, no writes, deploys or task runs.
- Sign-in with password and a mandatory authenticator code; roles checked on every API call; each account sees only its own data.
- Secrets encrypted at rest, TLS in transit (Caddy, Let's Encrypt), EU hosting, nightly backups encrypted on the server before they leave it (restic) and kept at another EU provider, restored into a throwaway database every week to prove they work. The master key is never in a backup.
- On the server only HTTPS (and SSH) is reachable: Postgres and the API publish no port, and passwords are mounted as files, never set as environment variables.
- No customer row data stored unless explicitly enabled per account.
- Full audit log: every change made through the app (connections, scans, pipelines, tests, runs, sign-offs, users and roles) and every sign-in, with who, when and from where; admins read and export it, nobody can change it in the app.
- Members can be limited to some spaces; a pipeline is visible to those who see its output's space.
- Sessions live as long as the browser window (no cookie lifetime), end after 60 minutes without use and after 12 hours at most; the cookie is Secure on a server. A user changes their own password (the current one and a code) and signs out their other browsers in Account. Passwords are at least 12 characters, not one or two characters repeated, and not made of the user's email.
- Sign-in is limited per address (30 a minute) and per email across addresses (20 every 15 minutes); a wrong password or code is written to the audit log of each of the user's accounts.
- What Ystara's operator does to an account (renaming it, inviting its admin, a reset link for one of its people) is copied into that account's audit log.
- Drafting scenarios with Claude sends pipeline definitions (never data) to Anthropic only after the account's admin switches it on, 50 drafts a day at most.
- A failure on Ystara's side answers with a reference and nothing of the cause; the reference finds it in the log. Caddy's log keeps invitation and reset tokens out.
- The containers drop every Linux capability and can't gain any; the API's filesystem is read-only.
- GDPR: `npm run user:erase` removes a person's sign-in and their name and address from the audit log and sign-offs; `npm run account:delete` removes an account with everything stored for it.
- CI fails on a known high or critical vulnerability in the packages a server runs (`npm audit --omit=dev`), and Dependabot proposes updates every week.
- Self-hosted runner available when required (same connector interface).

## Running in production

- **Health.** `GET /api/health` answers 503 when the API can't reach Postgres, and shows the version (the commit the image was built from). `GET /api/health/worker` answers 503 when no worker took the once-a-minute tick for 3 minutes. Docker restarts a stopped container; the uptime checks in `deploy/README.md` say when one keeps failing.
- **Restarts don't leave work hanging.** On a stop the worker takes no new job and gives the running ones 45 seconds. At every start, tick and stop it marks the scans, snapshots, runs, suites and checks that no job holds any more as interrupted ("Ystara restarted while it ran. Start it again."), so nothing shows "Running" forever (`sweepInterrupted` in `packages/db`).
- **A row and its job are saved together.** Starting a scan, snapshot, run, suite or check saves the row and queues its job in one transaction: there is never a queued scan without a job, or a job without its scan. The same scan, snapshot or Run all is refused while one is still running.
- **Time limits.** Every database statement stops after 30 seconds in the API and 5 minutes in the worker, a transaction left open after a minute, a migration that waits more than 10 seconds for a lock. A query on a tenant stops after 10 minutes, and mail and Teams calls after a minute.
- **Logs.** The worker writes one JSON line per event, with the queue and job; the API one per request, with its id, which every answer carries in `x-request-id`.
- **Paging.** Lists that grow (scans, snapshots, runs, suites) answer 50 at a time, newest first; `?before=<time>` gives the next 50.

## Feasibility spike results (2026-10-15)

The spike ran successfully against the partner tenant with Datasphere CLI 2026.x. Findings already reflected in the connector: `list`/`read` always return JSON (no `--output` flag), `list` needs `--top` beyond 25 items, and SQL and graphical views share the `views` command.

## Technical client spike results (2026-10-16)

Issam ran `npm run spike:technical-client` against the partner tenant with CLI 2026.21, a fresh CLI folder and the client in a secrets file. Findings reflected in the connector:

- `--host` goes after the command and its flags, for every command (the connector puts `--secrets-file` and `--verbose` there too). Before the command the CLI ignores the host: it asks "URL of the system to connect to" and exits with code 0. The old order only worked on a machine where `datasphere login` had stored a host.
- The CLI runs with no input. A question (a line starting with "?") or a `list`/`read` that isn't JSON is a failure even on exit code 0.
- With the host after the command, the client lists the views and local tables of a space it is a member of. `spaces list` and `spaces read` fail: they need a tenant-wide privilege, so scans and the spike don't rely on them.
