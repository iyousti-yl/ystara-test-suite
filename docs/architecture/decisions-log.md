# Decisions log

Short entries, newest first. One line of context, the decision, and why. Link the PR when there is one.

- **2026-10-16** Phase 1e, from Issam's run of the technical client spike on the partner tenant (PR #10; CLI 2026.21, a fresh CLI folder, the client in a secrets file). **The host goes after the command**: the connector puts `--host`, `--secrets-file` and `--verbose` after the command and its flags, for every command. Before the command the CLI ignores the host, asks "URL of the system to connect to" and exits with code 0; the old order only worked because the developer's CLI folder had a host stored by `datasphere login`. The CLI now runs with no input, and a question (a line starting with "?") or a `list`/`read` that isn't JSON is a failure even on exit code 0, with a message that says what the CLI did and never holds the client secret. **Ystara doesn't rely on `spaces list` or `spaces read`**: they need a tenant-wide privilege that a least-privilege technical client shouldn't get, so spaces are named by their IDs and the spike checks each one by listing its views and local tables (listing spaces only warns). **Issam approved the read-only gate change** that allows `config cache init` on 2026-10-16. That answers the open question of the entry below: a technical client that is a member of a space can list its objects. Still open: whether a Viewer-only client is enough.
- **2026-10-16** Phase 1e, part 1: **scans log in with a technical OAuth client** (Issam chose "Technical client" on the decision card). The Datasphere CLI accepts an OAuth client with the purpose "Technical User" through client credentials since 2024, so the worker can scan with nobody present; a person's login would stop scheduled scans whenever its refresh token expires. The client goes to the CLI in a secrets file inside a per-tenant CLI folder, so tenants never share a login and the folder (with the token) is deleted after the job. The read-only gate now also allows `config cache init`, which only downloads the tenant's list of CLI commands and is needed before any object command; it changes nothing in the tenant. Still open: whether a technical user added to a space can read its objects, which `npm run spike:technical-client` answers on the partner tenant.

- **2026-10-16** Polish from Issam's review of PR #4. Opening or closing the object panel keeps the picture's right edge (the output) in place and pans just enough to keep the selected object visible, rather than re-fitting and losing the zoom. Nodes are as wide as their technical name needs, and hovering a node shows its names at full size when the picture is zoomed out or a name is cut off. The Content-Security-Policy allows fonts and styles only from Ystara itself (no `https:`) and drops `upgrade-insecure-requests` while it runs on http://127.0.0.1. A task chain step that empties a table (DELETE_DATA) is a new `clears` edge instead of `triggers`, shown as "Cleared by task chains"; migration 002 allows it, and older scans show it after a rescan or re-import.
- **2026-10-15** Phase 1c, the lineage view in the web app (Claude's defaults, Issam to review). Pages for tenants, scans, objects and pipelines; the pipeline is drawn with React Flow and laid out left to right by dagre, opening on the output end at a readable size when the whole chain doesn't fit. Writers can be excluded with a click and the pipeline saved. The API now serves the web app on its own port and itself under `/api`, so there is no cross-origin traffic and CORS is gone. - **2026-10-15** Docker fixes from Issam's review of PR #3. Only the `migrate` service builds the image (the others reuse `ystara:dev`), so parallel builds can't race. Host ports come from `YSTARA_DB_PORT` (default 55432, away from a Postgres already on 5432) and `YSTARA_API_PORT` (4000); the same default is in the tools and `.env.example`. App settings and secrets move from `.env` to `.env.local`, because Compose reads `.env` and printed parts of secrets that contain `$`; `.env` may only hold `YSTARA_*`/`COMPOSE_*` keys and the tools refuse anything else. The API, worker and tools stop when the database has no `schema_migrations` or has pending migrations, and `db:migrate` refuses a non-empty database that was never migrated.
- **2026-10-15** **Local runs use Docker Compose** (Issam): Postgres, a one-shot `migrate` service, the API and the worker, published on 127.0.0.1 only until sign-in exists. The migrate step also creates the job queues, because the API and worker creating them at the same time deadlocked Postgres.
- **2026-10-15** Phase 1b storage: plain SQL with node-postgres and numbered SQL migrations (no ORM), PGlite for tests. Scans store every definition (once per tenant and hash) so the graph can be rebuilt with a newer parser. Pipelines store their output and writer exclusions; steps are computed from the latest successful scan. Accounts and sign-in come next, so tenants have no account yet.
- **2026-10-15** The connector's pipeline builder now applies the pipeline rules below (PR #2). Which writer belongs is configuration, not code: `--exclude-writer` or a git-ignored `tools/scan/scan.local.json`. Without it, every writer of a table is followed and the table is flagged as ambiguous, so nothing is silently dropped (Claude's default; revisit if ambiguous tables turn out to be common).
- **2026-10-15** **No tenant-specific content in the repository** (Issam). Object names, naming conventions and process rules of a tenant live in git-ignored local files (`.claude/tenant-conventions.local.md`, scan output), never in commits. Today we build against one tenant; the product must stay tenant-agnostic.
- **2026-10-15** **What a pipeline is** (Issam, after the first real scan of the partner space). Traced backwards from the output view through the main chain (view ← table ← its flow ← … ← ingestion tables ← the flows that load them). Config and control tables/views are side inputs and belong to the pipeline, with their own dependencies. Only the writer that belongs to the pipeline is followed; other writers of the same table belong to other processes and are excluded until they become relevant. Task chains are orchestration and are not part of the pipeline. References in SQL comments don't count. The scanner agent applies these rules; the pipeline builder in the connector still needs to.
