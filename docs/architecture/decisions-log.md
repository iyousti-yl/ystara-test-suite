- **2026-10-16** Operator fixes from Issam's review of PR #8. The operator can invite an admin only to an account with **no admin left** (checked with the account locked), so they can't make themselves admin of a customer and see its data. Reset links record the operator who made them and when they were used, stay on record after use, go into the log, and show on the account's Users and roles page; an operator's sign-in can't be reset from the panel, so one operator can't take over another. Reset links get a server-made authenticator secret like invitations, reset and invitation tokens are cut from the log, a new link closes older ones under a lock, and a new account comes with its first admin's invitation in one transaction. Migration 004 changed in place (not merged yet). Second review: an admin invitation from the operator is refused for someone already in the account (accepting never changes a member's role, so it would be used up and leave the account without an admin), and the Users and roles page lists every reset of the last 30 days, not only the latest.
- **2026-10-16** Sign-in fixes from Issam's review of PR #7. The authenticator secret is made by the server and kept sealed on the invitation; the browser shows it once and never sends it back, so nobody can choose a weak or shared one. Wrong codes count per user, across sign-ins: after five, codes lock for 1 minute, then 2, 4, ... up to an hour, and each lock ends the sign-in. An attempt is claimed before its code is checked, in one statement with the lock check (Issam's second review), so simultaneous requests can't check a sixth code. Rate limits count per address and per email, user or link, and the address comes from a proxy only when `YSTARA_TRUST_PROXY` names it (never "trust everyone"). Invitation tokens are cut from the request log. `MASTER_KEY` moves to its own git-ignored file `.master-key` (found through `MASTER_KEY_FILE`), and Docker Compose hands only that file to the API as a secret instead of mounting `.env.local`. Accepting an invitation never changes an existing member's role, removing a member ends their sessions, and an account with tenants can't be deleted (no cascade). Migration 003 changed in place (not merged yet): recreate a local database that ran it.
- **2026-10-16** Fixes to the **checks from Issam's review of #9**. "Before every push" is no longer only a convention: a **git pre-push hook** (`.githooks/pre-push`, turned on by the `prepare` script on `npm install`/`npm ci`, a no-op outside a git folder such as the Docker build) runs the tenant-content check on what each push adds (new `--head`, commits only), and **CI** runs it on every PR and push to main, where only the generic checks apply (no notes, scans or database). `git push --no-verify` skips the hook, as a last resort. The check got stricter: `--file` refuses `.env*`, `*.local.*` and scan output on the name alone, before reading (it prints matching lines, so it was a way around the `Read(.env.*)` deny); names match ignoring case; "already in base" needs the exact token in a base file outside `package-lock.json` (or, for an author, the same identity in base's history), because a case-insensitive search of the whole tree let short real names pass; only exact placeholder hosts are skipped (`your-tenant.`, `synthetic.`, SAP's bare `authentication.<region>.hana.ondemand.com`); 3-character names with a digit or underscore are looked for; commit authors and committers are checked; an added line that starts with `++` is no longer read as a file header. Claude Code permissions: the browser skill allows only the two `curl` preflight commands against 127.0.0.1 instead of `curl -s *`, and `git diff`/`git log` with `--output` (writes a file) and `git diff --no-index` (reads any file) are denied. The browser check's `--page` must be a path on the app ("/..."), so it never opens another site. The pure rules are in `tools/check/tenant-rules.ts` with tests, which `npm test` now runs for `tools/` too. Second review: `--file` reads only files inside the repository (and nothing in `.git`), because a path elsewhere, such as a worker's CLI folder with a client secret or `~/.git-credentials`, was read and its matching lines printed without a prompt; texts to check go in the git-ignored `tools/check/drafts/`.
- **2026-10-16** Phase 1e, part 2: the **Connect wizard** (Claude's defaults, Issam to review). Adding a tenant opens Connect, which says what a Datasphere admin creates (an OAuth client with the purpose Technical User, its technical user added to the spaces to scan) and takes the client ID, secret and token URL. The secret is sealed with `MASTER_KEY` and never sent back, not even to admins: changing the client means entering it again. The token URL must be on SAP's sign-in service (`*.hana.ondemand.com/oauth/token`), so a mistyped or hostile URL can't receive the secret. The worker checks a new client at once by listing the spaces it sees; the tenant page shows them and the scan dialog offers them. Admins connect, change and remove a client; anyone who may scan may check it again. A tenant without a client still scans with the CLI login of the worker's machine, for local development. The secret box moved to `@ystara/shared/secrets` because the worker now opens what the API sealed, so the worker needs `MASTER_KEY` too.

- **2026-10-16** Phase 1d, part 2: the **operator panel** (Issam chose "Both"). Ystara's operator is a flag on the user that only `npm run operator:grant` sets, so the web app can never make someone operator. The panel lists every account and user with counts only (members, admins, tenants, open invitations), never tenants, scans or pipelines, because the operator has no business in customer data. It creates accounts, invites a new admin to an account whose admins are gone, and makes one-time **reset links** (3 days, an earlier link stops working) for a lost password or phone. A reset replaces both the password and the authenticator and ends all of the user's sessions, because a lost phone and a leaked password look the same from here. The old sign-in keeps working until the link is used, so a reset requested by someone else locks nobody out (Claude's defaults).

- **2026-10-16** Phase 1e, from Issam's run of the technical client spike on the partner tenant (PR #10; CLI 2026.21, a fresh CLI folder, the client in a secrets file). **The host goes after the command**: the connector puts `--host`, `--secrets-file` and `--verbose` after the command and its flags, for every command. - **2026-10-15** **What a pipeline is** (Issam, after the first real scan of the partner space). Traced backwards from the output view through the main chain (view ← table ← its flow ← … ← ingestion tables ← the flows that load them). Config and control tables/views are side inputs and belong to the pipeline, with their own dependencies. Only the writer that belongs to the pipeline is followed; other writers of the same table belong to other processes and are excluded until they become relevant. Task chains are orchestration and are not part of the pipeline. References in SQL comments don't count. The scanner agent applies these rules; the pipeline builder in the connector still needs to.
