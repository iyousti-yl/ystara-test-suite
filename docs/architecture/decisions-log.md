- **2026-10-17** **GDPR: min and max are stored only as hashes** (Issam's choice, "Hash all"). A column's min or max can be a real value, so snapshots keep only a SHA-256 of a per-tenant salt and the value as text, made inside the tenant's database by the metrics query (`HASH_SHA256`), so the value never leaves it. Counts (rows, non-null, distinct) stay plain. Sums stay plain, except on objects with fewer than 10 rows (`SMALL_OBJECT_ROWS`), where one sum can be one person's figure: there the sum is hashed too. Equal hashes mean equal values, which is all a comparison of two snapshots needs; a hash says nothing about how far two values are apart. The salt is 32 random bytes per tenant, made on its first snapshot, sealed with `MASTER_KEY` for that tenant and never changed (another salt would change every hash); if the key can't open it, the snapshot fails rather than start over. Phase 2c, Claude's defaults (Issam to review): a snapshot measures every step of a saved pipeline that its space's database user sees and stores each step's definition hash from the latest scan, so a later comparison can tell a data change from a logic change; a step that can't be measured is stored with the reason the pipeline page gives. Each space's user signs in once per snapshot (no retries: repeated failed sign-ins can lock it). The snapshot fails when a measurable step couldn't be measured, or when no step could be, and keeps what it measured either way. Taking one needs the right to run tests; everyone in the account can read them.
- **2026-10-17** Phase 2b: **one database user per space**, entered on the tenant page (Claude's defaults, Issam to review). Datasphere names them SPACE#SUFFIX and each reads only its own space, so the space is taken from the name and there is no separate field. The host must be `<id>.hana.<region>.hanacloud.ondemand.com`, or `hna1`, `hna2`… in place of `hana` as on newer tenants (Issam's real host; `isDatabaseHost`), checked by the API, by the worker and by `SqlReader.connect` before any password is sent; port 443 only. The password is sealed for its tenant and space. The worker's `database-check` job signs in once (no retries: failed sign-ins can lock the user), fails a user with any privilege on the space's schema beyond SELECT, SELECT METADATA and SELECT CDS METADATA, and stores the views and tables it sees. **Which pipeline steps a snapshot can measure comes only from that list** (`measurability` in `@ystara/shared`): flows and task chains never (they hold no data), a step whose space has no checked user not yet, anything the user doesn't see "not exposed for consumption", with a hint that a modeler can expose a view. Ystara never exposes anything itself.

- **2026-10-16** Security fixes from Issam's review of PR #11 (Connect wizard). **No fallback to the worker's own login:** a tenant without a technical client is not scanned ("This tenant is not connected"), because a queued scan after the client was removed, or another account adding a tenant with the operator's host, would otherwise read with the operator's rights; only a worker started with `YSTARA_WORKER_MACHINE_LOGIN=1` (read once at start) uses its machine's CLI login, for local development. **Only SAP addresses:** a tenant URL must be `https://<tenant>.<region>.hcs.cloud.sap` (no IP, other host, port, path, query or credentials) and a token URL `https://<subdomain>.authentication.<region>.hana.ondemand.com/oauth/token`, so neither the bearer token nor the secret can reach an internal host or an app on `*.cfapps…hana.ondemand.com`; both rules live in `@ystara/shared` (urls.ts), the API checks them on input and the worker again before each login. **The CLI gets an allow-listed environment** (PATH and the Windows basics, proxy and CA settings, its home folders), never `MASTER_KEY`, `DATABASE_URL` or the rest of `.env.local`. **One masking function** (`maskSecrets` in the connector) hides the client secret as it is, URL-encoded and in base64 (also `clientId:secret`), plus Bearer/Basic headers, JWTs and `access_token`/`refresh_token`/`client_secret` values; it now covers every stored scan warning, not only errors. **Client secrets are sealed for their tenant** (AES-GCM additional data `tenant-connection:<id>`, tag length fixed at 16 bytes), so a sealed secret copied to another tenant's row doesn't open; authenticator secrets are unchanged. - **2026-10-15** **What a pipeline is** (Issam, after the first real scan of the partner space). Traced backwards from the output view through the main chain (view ← table ← its flow ← … ← ingestion tables ← the flows that load them). Config and control tables/views are side inputs and belong to the pipeline, with their own dependencies. Only the writer that belongs to the pipeline is followed; other writers of the same table belong to other processes and are excluded until they become relevant. Task chains are orchestration and are not part of the pipeline. References in SQL comments don't count. The scanner agent applies these rules; the pipeline builder in the connector still needs to.
