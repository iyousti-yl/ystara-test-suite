# Decisions log

Short entries, newest first. One line of context, the decision, and why. Link the PR when there is one.

- **2026-10-16** Sign-in fixes from Issam's review of PR #7. The authenticator secret is made by the server and kept sealed on the invitation; the browser shows it once and never sends it back, so nobody can choose a weak or shared one. Wrong codes count per user, across sign-ins: after five, codes lock for 1 minute, then 2, 4, ... up to an hour, and each lock ends the sign-in. Rate limits count per address and per email, user or link, and the address comes from a proxy only when `YSTARA_TRUST_PROXY` names it (never "trust everyone"). Invitation tokens are cut from the request log. `MASTER_KEY` moves to its own git-ignored file `.master-key` (found through `MASTER_KEY_FILE`), and Docker Compose hands only that file to the API as a secret instead of mounting `.env.local`. Accepting an invitation never changes an existing member's role, removing a member ends their sessions, and an account with tenants can't be deleted (no cascade). Migration 003 changed in place (not merged yet): recreate a local database that ran it.
- **2026-10-16** Phase 1d, sign-in, accounts and roles. **No public sign-up** (Issam, decision card "You create them"): the operator creates customer accounts with `npm run account:create`, which prints an invitation link for the first admin; admins invite the rest from the **Users and roles** page (Issam asked for an admin page for users and roles). Everyone signs in with email, password and an authenticator code; there is no "remember me" and no password reset by email yet (Ystara sends no email). A user can belong to several accounts with one role each and switches in the user menu. Every API route declares the permission it needs, and another account's data answers 404. Tenants from before sign-in move to an account named "Default" (migration 003). Next, in a second PR: an **operator panel** across all accounts (Issam chose "Both": accounts, users, a reset link for someone who lost their authenticator).

- **2026-10-15** Docker fixes from Issam's review of PR #3. Only the `migrate` service builds the image (the others reuse `ystara:dev`), so parallel builds can't race. Host ports come from `YSTARA_DB_PORT` (default 55432, away from a Postgres already on 5432) and `YSTARA_API_PORT` (4000); the same default is in the tools and `.env.example`. App settings and secrets move from `.env` to `.env.local`, because Compose reads `.env` and printed parts of secrets that contain `$`; `.env` may only hold `YSTARA_*`/`COMPOSE_*` keys and the tools refuse anything else. The API, worker and tools stop when the database has no `schema_migrations` or has pending migrations, and `db:migrate` refuses a non-empty database that was never migrated.
- **2026-10-15** **Local runs use Docker Compose** (Issam): Postgres, a one-shot `migrate` service, the API and the worker, published on 127.0.0.1 only until sign-in exists. The migrate step also creates the job queues, because the API and worker creating them at the same time deadlocked Postgres.
- **2026-10-15** Phase 1b storage: plain SQL with node-postgres and numbered SQL migrations (no ORM), PGlite for tests. Scans store every definition (once per tenant and hash) so the graph can be rebuilt with a newer parser. Pipelines store their output and writer exclusions; steps are computed from the latest successful scan. Accounts and sign-in come next, so tenants have no account yet.
- **2026-10-15** The connector's pipeline builder now applies the pipeline rules below (PR #2). Which writer belongs is configuration, not code: `--exclude-writer` or a git-ignored `tools/scan/scan.local.json`. Without it, every writer of a table is followed and the table is flagged as ambiguous, so nothing is silently dropped (Claude's default; revisit if ambiguous tables turn out to be common).
- **2026-10-15** **No tenant-specific content in the repository** (Issam). Object names, naming conventions and process rules of a tenant live in git-ignored local files (`.claude/tenant-conventions.local.md`, scan output), never in commits. Today we build against one tenant; the product must stay tenant-agnostic.
- **2026-10-15** **What a pipeline is** (Issam, after the first real scan of the partner space). Traced backwards from the output view through the main chain (view ← table ← its flow ← … ← ingestion tables ← the flows that load them). Config and control tables/views are side inputs and belong to the pipeline, with their own dependencies. Only the writer that belongs to the pipeline is followed; other writers of the same table belong to other processes and are excluded until they become relevant. Task chains are orchestration and are not part of the pipeline. References in SQL comments don't count. The scanner agent applies these rules; the pipeline builder in the connector still needs to.
