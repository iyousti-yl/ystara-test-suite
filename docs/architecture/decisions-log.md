- **2026-10-20** **Two agent and skill pairs for scenarios, and a skeleton to start one** (Issam: YAML by hand isn't practical, and "don't forget about creating specialist agents with skills"). The hard part of a scenario file is knowing every table and column name, so `npm run scenario:new` writes them from the saved scan: each table that takes rows, all its columns null with their types beside them, the steps that can be checked, and a first check that compiles. `--logic` prints each step's SQL or CSN query, upstream first. - **2026-10-19** **Phase 3a: running a scenario from the command line** (Issam: "ok, next?" after #24; Claude's defaults, for Issam to review). A scenario stays the YAML of `@ystara/shared` (fixtures, checkpoints, assertions), minus `run` and `truncate`, since nothing runs or loads in the tenant; unknown keys are refused, so a misspelt one isn't ignored. **A table the scenario gives no rows for is empty**, not filled with made-up rows, so a result depends only on what the scenario says. **Rows given for a table win over the transformation flow that loads it** (also in `spike:simulate --fixtures`), so a scenario can start in the middle of a pipeline. A fixture for a table outside the pipeline, for a view, or as CSV stops the whole scenario before anything is sent. Each assertion is one SELECT over its checkpoint's compiled query, built by the runner with quoted column names, and goes through the same last check as every compiled step (`assertSendable`: it reads only subqueries and DUMMY, and fits SAP HANA's limit of bound values). An `sql` assertion's own SELECT has `{{checkpoint}}` replaced by that subquery, and is refused when it has `?` placeholders or doesn't use `{{checkpoint}}`. `rows_equal` matches rows on the key, then compares the other columns the expected rows name; a number written as a number compares as a number (SAP HANA gives decimals as text), quoted text as text. `npm run scenario:run` prints pass, FAIL, ERROR or not run for each assertion. Storing scenarios, runs and their pages are phase 3b.

- **2026-10-19** **The read-only guard stays without WITH** (Issam, card "Keep guard"). When a pipeline's flows read the same steps many times, the spike's composed query can grow past the values SAP HANA binds to one statement, because each step's SQL is pasted wherever it is read. Allowing WITH in `assertSelectOnly` would write each step once, but Issam keeps the guard as it is. Instead, a step whose query would bind more than 32,767 values (`MAX_BOUND_VALUES`, taken as SAP HANA's limit for one statement until a real run shows otherwise) stops before anything is sent, with a sentence saying why, and so does every step that reads it. The steps before it still run, so such a pipeline is tested step by step up to that point.
- **2026-10-19** **Phase 3 spike: compiling a pipeline into fixture-only SELECTs** (Issam: "go ahead" on the spike the overview plans). The compiler lives in `packages/connector/src/simulate`, so the engine can grow from it; `npm run spike:simulate` runs it on a saved scan. Claude's defaults, for Issam to review: **nested subqueries, not WITH**, so the read-only guard stays as it is (a CTE needs a reviewed change to `assertSelectOnly`). **Fixture values are always bound** to `?` and cast to the column's SAP HANA type from the table's CSN, never written into the SQL; a value written in a view's own definition is copied as the view has it. **What stands in for a table:** the SELECT of the one transformation flow that loads it (a full load: a flow reading its own target sees it empty); otherwise a fixture, when nothing in the pipeline loads it, a data or replication flow does (those can't be expressed in SQL; snapshots cover them) or several flows do. - **2026-10-18** **Phase 2d: comparing two snapshots** (Issam's spec; design in the PR note). A pure function in `@ystara/shared` compares two stored snapshots of one pipeline; the API only reads them, with no tenant call. Each step gets a verdict: unchanged, data changed, definition changed, or both. The definition is its hash in the snapshot's scan. Data is the row count, every column measure, and the set of columns. Counts and hashes compare exactly. Steps measured in only one of the two are listed apart with the reason, and steps measured in neither still have their definitions compared. **Sums without false alarms:** HANA adds rows in no fixed order, so floating sums (DOUBLE, REAL, decimals without a scale) drift in their last digits. From now on a snapshot sums those as `SUM(CAST(c AS DECIMAL(38, 6)))`, which adds every value at a fixed 6 decimals and so is exact. The scale is stored with the sum. Integer and fixed-scale DECIMAL sums were already exact. So the comparison is exact at the stored scale, and two snapshots of the same data give the same sum, digit for digit.

- **2026-10-17** **GDPR: min and max are stored only as hashes** (Issam's choice, "Hash all"). A column's min or max can be a real value, so snapshots keep only a SHA-256 of a per-tenant salt and the value as text, made inside the tenant's database by the metrics query (`HASH_SHA256`), so the value never leaves it. Counts (rows, non-null, distinct) stay plain. Sums stay plain, except on objects with fewer than 10 rows (`SMALL_OBJECT_ROWS`), where one sum can be one person's figure: there the sum is hashed too. Equal hashes mean equal values, which is all a comparison of two snapshots needs; a hash says nothing about how far two values are apart. The salt is 32 random bytes per tenant, made on its first snapshot, sealed with `MASTER_KEY` for that tenant and never changed (another salt would change every hash); if the key can't open it, the snapshot fails rather than start over. Phase 2c, Claude's defaults (Issam to review): a snapshot measures every step of a saved pipeline that its space's database user sees and stores each step's definition hash from the latest scan, so a later comparison can tell a data change from a logic change; a step that can't be measured is stored with the reason the pipeline page gives. Each space's user signs in once per snapshot (no retries: repeated failed sign-ins can lock it). The snapshot fails when a measurable step couldn't be measured, or when no step could be, and keeps what it measured either way. Taking one needs the right to run tests; everyone in the account can read them.
